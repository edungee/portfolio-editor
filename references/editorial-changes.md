# Whole-portfolio editorial changes

The skill supports evidence-backed updates to any relevant portfolio surface through the host's repository tools. The existing pilot/preview/delivery scripts are a narrower milestone adapter; they do not implement arbitrary edits. For a mixed review or any unsupported surface, use this host workflow for the ENTIRE combined patch, instead of silently dropping candidates or running a milestone-only preview/delivery over a mixed PR.

## Evidence and copy

Review the site's structure and repository instructions. Map each included candidate to the right location: existing project history, a new case study, speaking/recurring series, writing or profile copy. Reuse existing components and content formats. Do not require a fabricated event date for an undated series or profile entry; dates are required only when the public claim is dated. Verify destination links and distinguish planned, recorded and published work. A source mention alone is not proof of authorship, launch, ownership or impact. Defer only the unsupported claim, not an independently supported description.

Use private `editorial-candidates.json` for evidence and decisions; it is never served or committed. Before delivery, compare all included candidate IDs against the patch and record each one's destination and status. Keep deferred/ignored reasons in REVIEW.md, while PR-SUMMARY.md describes all actual changes in public-safe language grouped by project or surface.

## One combined patch and preview

1. Read current default branch and existing managed PRs. If a PR is pending, inspect its head, files, body and review comments. Add new qualifying changes to that SAME draft PR when its remote head matches the last recorded head. Read any reviewer edits before updating; preserve them. If an unexpected head change prevents safe reconciliation, retain the new candidate privately and report the conflict. Do not force-push, discard edits, reopen a rejected PR or create a competing PR automatically. Previously rejected claims stay rejected unless explicitly reconsidered.
2. Use one clean isolated checkout. Start at the existing PR head, or current default branch for a new PR. Apply all accepted changes and stage only the exact reviewed file list. Inspect the complete diff against the current default branch, including earlier pending proposals. A changed default branch requires a refreshed combined baseline and validation; merge normally if necessary, never reset reviewer work.
3. Commit the combined patch locally. Save a private `editorial-snapshot.json`: repository, baseBranch, baselineCommit, expectedRemoteHead, branch, headCommit, includedCandidateIds, fileHashes (repository-relative path to SHA-256), routes, and contentId = SHA-256 of JSON {baseline, head, files} with sorted file keys. Paths must stay inside the checkout, be regular files, and exclude credentials, private evidence/config and unrelated files. Explicitly account for deletions if any. This is a host-managed manifest, not a batch-v1 report.
4. Archive that exact head into a new isolated preview directory outside Git; never reuse an old milestone-only site-preview. Add a public manifest containing only the opaque contentId. Keep evidence and review files outside the archive/server. Install dependencies or reuse only when manifests match. Run the site's production build in a separate checkout/build directory at the same head, and record outcomes.
5. Start the snapshot's dev server, retain process/session identity and verify HTTP status for all affected routes and the public contentId. Inspect changed pages in the browser. For a shareable preview use a temporary tunnel and verify it against that identity. Record URL, checkedAt, routes and sessions in the private snapshot. Label unavailable/expired links honestly. Content changes invalidate the previous preview; a tunnel replacement must serve the same approved snapshot.
6. Immediately before an ordinary fast-forward push, verify the remote base and expected PR head have not changed and that committed file hashes still equal the manifest. Create a new draft PR only if no matching open/closed PR exists. Otherwise update the existing draft's summary and links to cover ALL changes. Recheck remote PR head/base/draft/files and CI for that exact head; attach the PR when supported. No merge, ready-for-review or production deployment automatically.
7. Persist delivery-state with `adapter: host-editorial`, manifest path, PR identity, head, contentId, candidate IDs, preview and validation status. Future runs must follow this workflow for that PR: the milestone-only helper must not overwrite or describe a mixed-content PR. Mark each candidate delivered-to-draft only after remote verification, and implemented only after default-branch evidence. Save a notification fingerprint to avoid duplicate notifications.

The host performs these steps using its available Git, filesystem, preview and GitHub tools. No generic CMS adapter is claimed. Changes requiring unavailable access or an unsupported publishing platform remain explicit private proposals. Keep draft publication authorization separate from discovery authorization.
